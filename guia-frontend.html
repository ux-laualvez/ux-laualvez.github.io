Usás la escala de Tailwind pero con clases con nombre. Lo mejor de los dos mundos.

  Guardar cambios
</button>
Usás la escala de Tailwind pero el HTML sigue limpio con clases con nombre. Así trabaja shadcn/ui.

CSS semántico funciona bien cuando:

  • El proyecto tiene un sistema de diseño definido
  • El HTML tiene que ser legible sin conocer las clases de Tailwind
  • El equipo diseña los componentes desde cero y quiere control total

Tailwind es mejor cuando:

  • Trabajás en React/Next.js donde cada componente es un archivo
  • Querés que el estilo y la estructura vivan juntos en el mismo lugar
  • Querés iterar rápido sin saltar entre archivos
Por qué Tailwind domina en React: en React, cada componente es un archivo .jsx con su propio HTML y lógica. No hay un HTML global donde cargar un .css. Tailwind resuelve eso — el estilo viaja con el componente.

Dato: shadcn/ui

Es una librería de componentes para React que usa exactamente el patrón Tailwind + @apply que vimos arriba. En vez de darte un componente cerrado que no podés tocar, te da el código fuente directo — lo copiás, lo ajustás, lo hacés tuyo.

Hoy es el stack más común en proyectos React modernos: los componentes ya vienen con tokens de color, variantes y accesibilidad resueltos. Diseñadores que trabajan con devs en React lo van a ver mucho.

El mismo botón — con tokens vs sin tokens
La diferencia no se ve en el resultado visual. Se ve cuando cambiás el sistema.
Sin tokens — valores hardcodeados
.btn-primary {
  background: #2563eb;    /* ← hardcoded */
  color: #ffffff;          /* ← hardcoded */
  padding: 0 16px;         /* ← hardcoded */
  border-radius: 6px;      /* ← hardcoded */
  font-size: 14px;         /* ← hardcoded */
}
Si el color de marca cambia a verde, hay que buscar #2563eb en todos los archivos y reemplazarlo. En un sistema grande: horas de trabajo y bugs garantizados.
Con tokens — valores con nombre
tokens.css — acá se definen los valores
:root {
  --primary: #2563eb;
  --space-4: 16px;
  --radius-md: 6px;
  --text-sm: 14px;
}
components.css — acá se usan
.btn-primary {
  background: var(--primary);     /* ← token */
  color: var(--primary-fg);       /* ← token */
  padding: 0 var(--space-4);      /* ← token */
  border-radius: var(--radius-md);/* ← token */
  font-size: var(--text-sm);      /* ← token */
}
Si el color de marca cambia, se cambia --primary en tokens.css — un solo lugar — y se actualiza en todo el sistema. Botones, badges, links, focus rings — todo.
Tres posturas frente a Tailwind y los tokens:
Usar Tailwind tal cual
Aceptás su escala como tus tokens. Rápido, pero perdés control de marca. Los valores son de Tailwind, no tuyos.
Extender Tailwind ← más común
Agregás tus tokens encima de los suyos en tailwind.config.js. Podés usar bg-primary con tu color de marca.
Reemplazar Tailwind
Desactivás sus defaults y ponés solo tus tokens. Máximo control, más trabajo inicial.

¿Flex o Grid? — y cuándo decidirlo
Usá Flex cuando…
→ Es una fila de elementos: botones, tabs, nav, tags
→ Es una columna de elementos: lista, form, sidebar
→ Necesitás centrar algo (horizontal + vertical)
→ El contenido tiene tamaños variables
Usá Grid cuando…
→ Tenés una galería de cards iguales
→ Tenés el layout de la página (sidebar + contenido)
→ Necesitás que algo ocupe varias columnas (merge)
→ Las columnas tienen ancho fijo definido por vos
¿Lo decidís al principio o lo cambiás después?
Podés empezar todo en flex y agregar grid después — cambiarlo es fácil. Cambiar un flex por grid grid-cols-3 es literalmente editar una clase. Pero hay dos momentos donde conviene decidir antes de arrancar:
  • El layout de la página (sidebar + contenido main) — si empezás con flex y después querés grid, puede requerir reestructurar el HTML
  • Galerías de cards — si ya escribiste el markup con flex y el cliente quiere merge cells, el cambio es mínimo en CSS pero puede requerir ajustes en el HTML
Regla práctica: si al mirar el diseño pensás "esto es una fila de cosas" → flex. Si pensás "esto es una grilla" → grid. En todo lo demás, flex por defecto. Con Claude el costo de cambiar es casi cero — es una edición de clase, no reescribir el componente.

React, frameworks y estructura de proyecto

Por qué existe React, qué es un framework, cómo elegís el correcto y cómo se ve un proyecto por dentro.

Qué es un "framework" — la palabra que aparece en todos lados
En desarrollo web aparece constantemente en contextos distintos. No es una sola cosa — son tres capas, y en un proyecto real podés tener las tres juntas.
Un framework es una estructura pre-armada con reglas y convenciones. En lugar de tomar mil decisiones desde cero — ¿cómo organizo las carpetas? ¿cómo conecto una URL a una página? — el framework ya las tomó. Vos seguís las reglas y te concentrás en construir.
CapaEjemploQué regula
Estilos Tailwind Cómo escribís CSS — la escala, las clases, los tokens
Componentes React Cómo construís y conectás componentes reutilizables
Proyecto completo Next.js, Astro, Vite Cómo se organiza el proyecto, las páginas, el routing, la compilación
"Next.js + React + Tailwind" = tres frameworks, tres capas, un solo proyecto. Next.js usa React para los componentes, React usa Tailwind para los estilos.
Cuatro tipos de proyecto — cuatro frameworks
La pregunta clave no es "¿qué es más moderno?" sino una sola: ¿Google necesita indexar esto? Si aparece en búsquedas → sí. Si está detrás de login → no. Eso determina casi todo lo demás.
Pieza o prototipo
HTML + Tailwind
Una sola pantalla, exploración rápida, validación de concepto. No hay routing, no hay componentes que compartir entre páginas.
Ej: landing de evento, email, card suelta, prototipo de UI
Google: no importa
Site de contenido
Astro
Muchas páginas, contenido que no cambia según quien lo lee. Velocidad y SEO son lo más importante. Casi sin interactividad. Astro envía cero JavaScript al browser por defecto.
Ej: blog, docs, portfolio con muchas entradas, Wikipedia-style
Google indexa → SEO crítico
Web de producto o app pública
Next.js
Páginas públicas que Google indexa + partes interactivas + posiblemente sección privada con login. El más versátil y el estándar hoy.
Ej: Airbnb, GitHub, Stripe, web de startup, e-commerce, Notion.so
Google indexa + interactividad
App detrás de login
Vite + React
App compleja que vive detrás de un login. Google no la puede indexar — nadie busca en Google el contenido de su inbox. Priorizás performance de la app, no SEO.
Ej: Gmail, Figma app, Linear, el editor de Notion, dashboard interno
Nadie busca tu inbox en Google
Un producto puede tener las dos partes: Airbnb.com (listados públicos) → Next.js porque Google indexa los departamentos. El panel del host (detrás de login) → podría ser Vite. Notion.so (marketing) → Next.js. El editor de Notion (la app) → Vite + React. No es uno o el otro — es según la parte del producto.
Todo termina en HTML
Lo que el browser siempre recibe es HTML + CSS + JS. El framework — Next.js, Astro, Vite — traduce lo que vos escribís al formato que el browser entiende. Vos escribís la UI — componentes, layout, interacciones —; el framework hace la conversión.

Cómo elegir qué componentizar
El criterio es casi idéntico al de Figma. Si en diseño lo hubieras hecho componente, en React también.
¿Aparece más de una vez? → componente. Un Button que usás en 10 páginas = un archivo Button.tsx.
¿Cambia según contexto? → componente con props. Si tiene variantes (tamaño, color, estado), es un componente con props — no varios archivos separados.
¿Es único en toda la app, nunca se repite? → puede ir directo en la página, sin crear un archivo aparte.
Regla rápida: si en Figma lo hubieras componentizado, en React también. El instinto de diseñadora aplica directo.
Componentes — cómo se construyen y usan
Un archivo por componente. Las variantes adentro vía props — igual que las component properties de Figma. Los estilos (Tailwind) adentro también. Todo junto en un solo lugar.
Figma — Component properties
Component properties
variant primary / ghost
size sm / md / lg
label text
Seleccionás la instancia → ves estas propiedades en el panel derecho de Figma
React — Props en Button.tsx
export function Button({ variant, size, label }) {
  return (
    <button className={styles[variant][size]}>
      {label}
    </button>
  )
}

// Se usa así:
<Button variant="primary" size="md" label="Guardar" />
<Button variant="ghost" size="sm" label="Cancelar" />
Props = component properties de Figma. Tailwind va directo en el JSX — los estilos no viven en un CSS separado, viven en el componente. En HTML puro necesitabas saltar entre dos archivos para entender un componente; en React todo está junto.

public/ (la carpeta) ≠ páginas públicas (sin login)
Son dos usos completamente distintos de la palabra "público". La carpeta public/ es donde viven los archivos estáticos (imágenes, fuentes). No tiene ninguna relación con si la página requiere login o no.
Qué va en public/
public/images/ — fotos, ilustraciones, backgrounds
public/fonts/ — fuentes custom (si no usás Google Fonts)
public/favicon.ico — el ícono del tab del browser
Qué NO va en public/
Íconos de UI (botones, nav) → usás Lucide o Heroicons como componentes, no archivos locales
Muchas imágenes (e-commerce) → usás un CDN externo como Cloudinary, no archivos en la carpeta
Páginas públicas, privadas y flows — en las carpetas
La arquitectura de información de Figma — qué es público, qué requiere login, qué es un flow de pasos — se mapea directamente a la estructura de app/.
app/
 ├── (público)/  ← sin login
 │   ├── page.tsx → /
 │   └── precios/page.tsx
 ├── (privado)/ ← requiere login
 │   ├── dashboard/page.tsx
 │   └── configuracion/page.tsx
 └── checkout/ ← flow de pasos
     ├── carrito/page.tsx
     ├── envio/page.tsx
     └── confirmacion/page.tsx
(público) — sin login
Los paréntesis agrupan páginas sin aparecer en la URL. Cualquiera puede entrar.
(privado) — requiere login
Next.js chequea si el usuario está autenticado antes de cargar. Si no → lo manda al login.
checkout/ — flow de pasos
Cada paso = una página. La lógica de "no podés saltear el paso 2" se maneja en el código — Next.js solo da la estructura.
Los tipos de archivo — qué hace cada uno
Ahora que ves la estructura del proyecto, cada extensión tiene un lugar y un rol claro.
Extensión Qué hace Dónde aparece Regla simple
.html Estructura y contenido Proyectos simples, páginas estáticas esto existe
.css Estilos visuales globals.css, tokens.css así se ve
.js / .ts Lógica, interacciones, cálculos Scripts, helpers, configuraciones hacé algo
.jsx / .tsx Componente React — HTML y lógica en un mismo archivo Button.tsx, Card.tsx esto existe + hacé algo
.json Datos estructurados. Sin lógica, solo valores package.json, tokens.json esta es la info
.md Documentación en texto. Como un README o esta guía README.md, notas del proyecto leé esto
.tsx vs .jsx — son lo mismo, pero .tsx usa TypeScript: una versión de JS con más validaciones. En proyectos modernos vas a ver casi siempre .tsx. No hace falta aprenderlo ahora — solo reconocerlo.
.json no es código — es más parecido a un .md que a un .js. Solo guarda información estructurada: listas, valores, pares clave-valor. El programa lo lee, pero el JSON mismo no hace nada.
Próximo paso: el backend
Todo lo que vimos hasta acá — componentes, layout, estructura de proyecto — es el frontend: lo que se ve y se construye. Pero dos preguntas que aparecen enseguida llevan al siguiente nivel.
¿Dónde pongo el contenido?
Depende de a quién le pertenece y si cambia. Hay tres casos:

Lo ven todos igual — los textos de la UI, los labels, los mensajes de error. Van en el código, los escribís vos.

Lo carga el usuario y es suyo — su nombre, su historial, sus pedidos. Es personal, cambia por usuario. Vive en una base de datos.

Lo genera el sistema — el estado de una compra, una notificación, un precio actualizado. Nadie lo escribe a mano: se produce solo según lo que pasa en la operación. También vive en una base de datos.
¿Cómo reacciona la interfaz a lo que pasa?
Todo lo que vimos es estático — el componente siempre se ve igual. En una app real cambia: un pedido pasa de "en preparación" a "despachado", un usuario sube una foto de perfil, un carrito se actualiza. Eso es state — la parte del componente que puede cambiar en respuesta a algo. Cuando ese "algo" viene de un servidor, el frontend necesita pedírselo. Ahí empieza el backend.
Frontend → Backend → Base de datos. El backend es el intermediario: decide qué datos puede ver cada usuario y devuelve solo lo que corresponde. Sin él, cualquiera podría acceder a los datos de cualquier otro.
